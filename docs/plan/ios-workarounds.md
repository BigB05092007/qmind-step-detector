# On-board iOS step detector: running live with the phone in a pocket

Scope: QMIND x Geotab step detector (orientation.py / steps.py port, 100 Hz, 2 s windows). Hard constraint: raw `CMMotionManager.startAccelerometerUpdates` -> `CMAccelerometerData.acceleration` (G, gravity included) feeds the team's own orientation code; CMDeviceMotion / CMPedometer / CMMotionActivityManager are comparison only. Every claim below carries a status: VERIFIED (fetched in this workflow) or UNVERIFIED (snippet/memory). Apple statements and developer reports are labelled separately. Quotes are collected in section 6.

## 1. Bottom line

For the class demo (Xcode/ad-hoc install, no App Review) use the **location keep-alive**: declare `UIBackgroundModes = location`, start a When-In-Use standard location session in the foreground with `allowsBackgroundLocationUpdates = true` and `pausesLocationUpdatesAutomatically = false`, then run one `CMMotionManager` at `accelerometerUpdateInterval = 0.01` on a serial background queue — this is the only mechanism with an Apple DTS "the system is designed to work this way" plus a modern measurement (iOS 26.5.2: 99.5 % of CoreMotion callbacks delivered in the background vs 0.16 % without), and it genuinely lets the phone be locked in a pocket. If the app were ever shipped on the App Store, keep the same mechanism but make the location data a real feature (GPS route/distance/pace next to the cadence, Apple's own "Track the precise path taken during a hike or fitness workout" case) and optionally add an audible cadence click under the `audio` mode as a second keep-alive; a pure keep-alive with discarded location data is a documented 2.5.4 rejection. The single biggest risk is that **no source has measured 100 Hz raw `startAccelerometerUpdates` delivery with the screen locked on iOS 16+** (the only measurement is CMDeviceMotion at ~10 Hz), so the first task is a 10-minute pocket spike that logs `CMAccelerometerData.timestamp` gaps on the team's own phones, with the Guided Access foreground kiosk (no plist keys, no permissions) as the always-works fallback.

## 3. Recommended architecture

### 3.1 Keep-alive: standard location service, started in the foreground

- `Info.plist`: `UIBackgroundModes = [location]` (Xcode: Signing & Capabilities > Background Modes > Location updates). Apple: setting `allowsBackgroundLocationUpdates = true` without the key "is a fatal error that terminates the app" (VERIFIED).
- `Info.plist`: `NSLocationWhenInUseUsageDescription` (required by `requestWhenInUseAuthorization()`, VERIFIED) and `NSLocationAlwaysAndWhenInUseUsageDescription` (Apple's plist page says to use it when location is needed in the background, VERIFIED) — ship both, request only When In Use at runtime.
- Foreground, after authorization: `desiredAccuracy = kCLLocationAccuracyBest` for the demo's route/pace feature (or `kCLLocationAccuracyThreeKilometers` + `distanceFilter = 3000` for the exact iOS 26.5.2-measured low-power configuration if the route feature is dropped), `distanceFilter = kCLDistanceFilterNone`, `activityType = .fitness`, `pausesLocationUpdatesAutomatically = false` (default true; a pause ends When-In-Use background access until relaunch, VERIFIED), `allowsBackgroundLocationUpdates = true`, `showsBackgroundLocationIndicator = true` (the Apple-stated escape hatch from the iOS 16.4 low-accuracy suspension rule, VERIFIED), then `startUpdatingLocation()`. Never also call `startMonitoringSignificantLocationChanges()` (iOS 16.4 suspension trigger, VERIFIED).
- `startUpdatingLocation()` must be called in the foreground before the phone is pocketed (Apple: "Attempts to start location updates while your app runs in the background will fail"; DTS Mar 2025: otherwise updates stop after a few seconds; VERIFIED).
- Keep `didUpdateLocations` and the accelerometer handler cheap; run the 2 s window FFT on a separate utility queue (DTS Jun 2025: slow delegate processing eventually stops location updates, VERIFIED).
- Surface `CLLocationManager.authorizationStatus`, `ProcessInfo.processInfo.isLowPowerModeEnabled`, `thermalState`, `UIDevice.current.batteryLevel` and the measured Hz in the UI. Denied location = the keep-alive silently fails at screen lock (OptimalRunning comment, VERIFIED OSS).

### 3.2 CoreMotion calls (the pedagogical core)

Exactly one `CMMotionManager` (Apple: "Create only one CMMotionManager object for your app", VERIFIED). No `NSMotionUsageDescription` is needed for this call (Apple lists the key only for CMSensorRecorder, CMPedometer, CMMotionActivityManager, CMMovementDisorderManager, VERIFIED); it becomes mandatory the moment CMPedometer or CMSensorRecorder are added for ground truth (app crashes otherwise, VERIFIED).

```swift
final class RawAccel {                                   // one instance for the whole app
    private let mm = CMMotionManager()
    private let q: OperationQueue = { let q = OperationQueue(); q.maxConcurrentOperationCount = 1
        q.qualityOfService = .userInitiated; return q }()
    var onSample: ((Double, SIMD3<Double>) -> Void)?      // (t seconds since boot, m/s^2 incl. gravity)
    func start() {
        guard mm.isAccelerometerAvailable else { return }
        mm.accelerometerUpdateInterval = 0.01             // 100 Hz; 40/100 Hz honoured exactly
        mm.startAccelerometerUpdates(to: q) { [weak self] d, _ in
            guard let d else { return }                   // use d.timestamp, never Date()
            let a = d.acceleration
            self?.onSample?(d.timestamp, SIMD3(a.x, a.y, a.z) * 9.80665)
        }
    }
    func stop() { mm.stopAccelerometerUpdates() }
    func restart() { stop(); start() }                   // called on didEnterBackground / didBecomeActive
}
```

Downstream: the Swift port of `gravity_lowpass -> vertical/horizontal split -> 2 s window (N=200 DFT) -> cadence -> classify -> peak count`, fed by timestamp (build windows from `timestamp` deltas, not an assumed 10 ms; Apple: "always check the timestamps", VERIFIED).

### 3.3 Transition handling

- Observe `UIApplication.willResignActiveNotification`, `didEnterBackgroundNotification`, `willEnterForegroundNotification`, `didBecomeActiveNotification` (locking the device fires resign-active per Apple and did-enter-background per a Nov 2023 report; there is no screen-off notification, DTS May 2024; all VERIFIED). Log each with the current sample count.
- On `didEnterBackground` and on `didBecomeActive`: `restart()` the accelerometer stream (iOS 11 and iOS 13.1 reports of CoreMotion dying on the transition even with location/audio modes; LAMP-swift and sensormore do exactly this; no iOS 16+ report either way; cheap insurance).
- Keep the location configuration constant for the whole session (DTS Oct 2024: altering the configuration can end the When-In-Use session, VERIFIED).
- Watchdog on the sample queue: if no sample for > 1 s while `isRecording`, log a gap event, call `restart()`, and raise the fallback flag (3.5).
- Test launched from the Home screen with no debugger: with Xcode attached the app is never suspended and the failure is masked (iOS 26.5.2 measurement, VERIFIED).

### 3.4 How the count reaches the user while locked

Honest position: with the screen locked in a pocket nothing is visible, so the live count is **computed** live and **shown** on reveal (unlock -> app foreground -> live chart and running count, plus a per-window timeline for the pocketed interval). Channels, in order of evidence:

1. In-app display on reveal (always works; the app process never stopped, so the count is continuous).
2. Audible cadence click or periodic spoken "cadence 110, 540 steps" through headphones — the only verified in-pocket feedback channel; requires adding `UIBackgroundModes = audio` with a `.playback` + `.mixWithOthers` session and an always-rendering AVAudioEngine (DTS: audio keeps the app awake "exactly the same" as location, so this is also a second keep-alive). Handle `AVAudioSession.interruptionNotification` (.ended + .shouldResume -> restart engine). Do not deactivate the session on a lock-screen Pause (ends the keep-alive).
3. Live Activity / Dynamic Island: optional cosmetic only. Updates from a background audio app are reported to be forbidden (developer report, Apr 2024); under a location keep-alive it is untested. Invisible in a pocket anyway. Build only if time remains.
4. Haptics: not available (Apple Frameworks Engineer: no haptics unless foreground-active, VERIFIED). Do not plan on them.

### 3.5 Fallback chain when the mechanism fails

```
location keep-alive (live, 100 Hz raw)
  -> watchdog gap > 1 s or lifecycle shows suspension
     -> [if audio mode present] audio keep-alive is already running; log which assertion held
     -> on next foreground: CMSensorRecorder catch-up (50 Hz raw, FS=50 constants, up to 3 min lag,
        A10+ only; requires NSMotionUsageDescription + Motion & Fitness + Fitness Tracking on)
        -> CMPedometer.queryPedometerData(from:to:) as the "Apple says" comparison column
           (also the recommended way to trigger the Motion & Fitness prompt)
  -> zero-permission fallback for demo day: Guided Access kiosk (foreground, isIdleTimerDisabled,
     brightness 0, Side button + Touch off, Display Auto-Lock Never) — no plist keys at all
```

Arm the recorder (`CMSensorRecorder().recordAccelerometer(forDuration: 12*3600)` off the main thread) on Start and in `sceneDidEnterBackground`; on `sceneWillEnterForeground` query `[anchor, min(now, anchor+12h)]`, dedupe by `startDate`, split windows on gaps > 2 samples, and run the FS=50 pipeline (local probe: walk 33 vs 36, run 48 vs 50 steps against the 100 Hz path, bin spacing stays 0.5 Hz). Display both counts side by side with the lifecycle log so the demo can explain any difference.

## 5. Validation protocol (do this before building the app)

Throwaway spike app `AccelSpike` (one screen: Start/Stop, keep-alive picker: none / location-3km / location-best / audio-silent / audio-click, status line). It writes `spike_<config>_<phone>_<ios>.csv` to the Documents folder (share via Files app), one row per sample: `t_boot (CMAccelerometerData.timestamp), t_wall (Date()), x, y, z` plus event rows `EVENT,<t_boot>,<willResignActive|didEnterBackground|willEnterForeground|didBecomeActive|locationAuth=<status>|audioInterruption=<began|ended>|restart>`; a 1 Hz heartbeat row with `batteryLevel`, `thermalState`, `isLowPowerModeEnabled`, sample count. Writes are buffered (append every 1 s from the serial queue).

Procedure, per phone model and iOS version on the team (each run launched from the Home screen, Xcode NOT attached, Low Power Mode off):

1. Control A, screen on, phone in hand on a table, 2 min — establishes the achievable rate.
2. Control B, keep-alive = none, press side button, pocket, 2 min — must show the stream dying (expected: callbacks stop within seconds; iOS 26.5.2 measurement 0.16 %). If it does not die, the debugger is attached or the test is invalid.
3. Main run, keep-alive = location-best (and separately location-3km), tap Start, wait for the blue pill, press side button, phone in trouser pocket, walk 10 min outdoors, then 10 min indoors (no GPS fix; a 2022 report saw updates stop indoors after minutes).
4. Audio run, keep-alive = audio-silent then audio-click, same 10 min; during the run take a 30 s phone call and play Music for 1 min (interruption + mixing test).
5. Guided Access run (foreground kiosk, no keep-alive, Guided Access with Side button + Touch off, Display Auto-Lock Never), 15 min in pocket — proves the fallback and checks the iOS 12-era blanking bug on the team's iOS.

Analysis script (Python, reuse the team's tooling): `dt = diff(t_boot)`; report sample count vs expected (`600 s x 100 Hz = 60 000`), delivery ratio, median dt, p99 dt, a gap histogram with bins `< 15 ms`, `15–50 ms`, `50–500 ms`, `0.5–2 s`, `> 2 s`, the longest gap, number of gaps > 100 ms, and gaps aligned with EVENT rows.

Pass/fail for the main run (per phone):
- PASS: delivery ratio >= 99.0 % (>= 59 400 samples in 10 min), median dt = 10.0 ± 0.5 ms, p99 dt <= 20 ms, no gap > 2.0 s (one 2 s window), at most 5 gaps > 100 ms, and the lifecycle log shows `didEnterBackground` followed by continuous samples.
- MARGINAL (usable with the restart watchdog): delivery 95–99 %, or gaps > 2 s only at lifecycle transitions.
- FAIL: delivery < 95 %, any gap > 30 s, or sample rate collapses below 50 Hz in the background. A FAIL on location-best but PASS on audio means switch the primary keep-alive; FAIL on both means ship the Guided Access kiosk for the demo and the CMSensorRecorder catch-up for the pocket interval.
- Control B must FAIL (otherwise the harness is wrong).
- Battery: record level at start/end; flag if a 20-minute run costs more than 10 % (no verified reference number exists; the only figure is an UNVERIFIED 2016 snippet of ~3 %/h for the accelerometer alone).
- CPU: with the real pipeline attached, each 2 s window must process in < 5 ms on the utility queue (keeps the delegate cheap per DTS).
